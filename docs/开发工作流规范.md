# SmartHR-Agent-all 开发工作流规范

## 1. 目的

本规范用于保证企业级智能招聘平台在持续开发过程中具备清晰的功能边界、开发历史和项目进度，避免出现上一个功能尚未完成就直接开始下一个功能、代码与文档脱节、提交历史难以追踪等问题。

仓库级强制规则见根目录 `AGENTS.md`，本文件对实际执行流程进行补充说明。

## 2. 工作流总览

```text
读取项目进度
    ↓
检查上一个功能是否已收口
    ├─ 否 → 说明未完成项 → 询问用户是否确定切换
    │                         ├─ 否 → 继续收口原功能
    │                         └─ 是 → 记录用户决定后继续
    └─ 是
        ↓
确认新功能范围与验收标准
        ↓
创建独立功能分支
        ↓
登记项目进度
        ↓
开发、测试、同步文档
        ↓
进入待验收
        ↓
用户确认
        ↓
中文提交与推送
        ↓
使用 --no-ff 合并
        ↓
更新进度为已收口
```

## 3. 新功能开始前检查表

- [ ] 已完整阅读 `docs/项目进度.md`。
- [ ] 已确认当前是否存在“进行中”“阻塞”或“待验收”的功能。
- [ ] 上一个功能已经标记为“已收口”。
- [ ] 如果上一个功能未收口，已经向用户说明情况并获得明确决定。
- [ ] 已阅读与新功能有关的需求和设计文档。
- [ ] 已明确业务目标、开发范围和非目标。
- [ ] 已明确验收标准。
- [ ] 对存在歧义的内容已经向用户提问并得到答案。
- [ ] 正式开发时已从主分支创建独立功能分支。
- [ ] 已在进度文档中登记新功能和分支。

## 4. 未收口功能的处理方式

发现上一个功能未收口时，不直接开始下一个功能。应向用户提供以下信息：

```text
当前功能“<功能名称>”尚未收口。
当前状态：<进行中/阻塞/待验收>
尚未完成：<未完成事项>
可能影响：<切换功能产生的影响>

是否确定暂停当前功能并开始“<新功能名称>”？
```

只有用户明确表示继续新功能后，才能执行以下操作：

1. 在进度文档中记录暂停原因和用户决定。
2. 将原功能保留为真实状态，不能虚假标记为已收口。
3. 再为新功能创建分支和登记进度。

## 5. 需求澄清规则

出现以下情况时必须立即提问：

- 同一句需求存在两种以上合理解释。
- 需求与已有业务规则或文档冲突。
- 不同选择会明显改变数据模型、接口或页面交互。
- 缺少必要的角色、权限、状态或异常处理规则。
- 无法确定验收成功的标准。
- 操作可能造成数据丢失、兼容性问题或较大返工。

提问时说明“哪里不清楚、有哪些影响、需要用户决定什么”，不要仅笼统地说需求不明确。

## 6. 分支管理

### 6.1 分支类型

| 类型 | 格式 | 用途 |
| --- | --- | --- |
| 功能 | `codex/feature-xxx` | 新增业务功能 |
| 修复 | `codex/fix-xxx` | 修复明确缺陷 |
| 重构 | `codex/refactor-xxx` | 不改变业务行为的结构调整 |
| 文档 | `codex/docs-xxx` | 独立的较大文档工作 |

### 6.2 分支原则

- 正式功能开发必须创建独立分支。
- 单个分支只处理一个功能或一组不可分割的相关改动。
- 分支创建前确认主分支状态和当前工作区，避免覆盖用户已有改动。
- 未经用户允许，不删除、重置或覆盖用户分支与改动。
- 仅讨论、规划和建立规范时，不强制创建分支。

## 7. Git 文件跟踪范围

仓库只跟踪能够复现、理解、开发和验证项目所必需的文件。

应提交到 Git：

- 业务源码、测试源码和数据库迁移脚本。
- `docs/` 下的需求、设计、进度和使用文档。
- `AGENTS.md`、`.gitignore` 等仓库级规则。
- 依赖清单、锁文件、构建配置和应用配置模板。
- `.env.example`、`.env.template`、`.env.sample` 等安全环境模板。
- 项目运行必需且没有安全风险的静态资源。

应加入 `.gitignore`：

- 真实环境变量、密钥、证书和本地私有配置。
- 依赖目录、构建目录、编译文件和发布压缩包。
- 日志、缓存、临时文件、测试报告和覆盖率产物。
- IDE、编辑器和操作系统生成的个人文件。
- 本地数据库、上传文件以及运行时生成的数据。

引入新的语言、框架或开发工具时，应同步检查 `.gitignore`。环境模板只允许出现安全占位值，不允许为了方便而复制真实环境配置。

## 8. 提交规范

提交信息统一使用中文，推荐使用“类型 + 范围 + 中文说明”：

```text
feat(招聘需求): 支持用人经理提交招聘申请
fix(候选人): 修复重复简历合并后标签丢失问题
docs(项目): 更新招聘需求功能验收结果
test(面试): 增加面试状态流转测试
refactor(权限): 统一候选人数据范围校验
```

常用类型：

| 类型 | 用途 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `docs` | 文档改动 |
| `test` | 测试改动 |
| `refactor` | 重构 |
| `chore` | 工程配置或辅助工作 |

推送和交付说明同样使用中文。推送前确认当前分支、提交内容、测试结果和进度文档均正确。

## 9. 合并规范

功能验收后，优先使用非快进合并保留分支节点：

```bash
git switch <目标分支>
git merge --no-ff <功能分支> -m "merge(<功能范围>): 合并<功能名称>"
```

这样可以在 Git 网络图中清晰看到每个功能的开始、开发提交和合并节点。

合并前检查：

- [ ] 工作区没有误改或未说明的文件。
- [ ] 功能验收标准全部有结果。
- [ ] 必要测试已经通过。
- [ ] 进度文档已经同步。
- [ ] 提交信息和合并信息使用中文。
- [ ] 已明确遗留问题及其优先级。

## 10. 进度同步规范

每批代码、配置、测试或重要文档发生实际改动后，都应同步维护 `docs/项目进度.md`。进度文档不记录流水账，重点记录能帮助下一个会话快速恢复上下文的信息：

- 当前正在做什么。
- 为什么做。
- 已经完成什么。
- 还缺什么。
- 如何验证。
- 当前在哪个分支。
- 有没有阻塞和需要用户决定的问题。
- 下一步应该做什么。

## 11. 功能验收与收口

### 11.1 进入待验收

完成实现、自测和文档同步后，将功能状态更新为“待验收”，并向用户说明：

- 已完成内容；
- 验证方式与结果；
- 仍存在的限制或遗留事项；
- 需要用户确认的验收内容。

### 11.2 标记已收口

功能达到 `AGENTS.md` 中的收口标准后，更新为“已收口”。如果还有用户要求必须完成的事项，不得仅因为主要代码已经写完就标记为已收口。

## 12. 异常情况

### 12.1 紧急修复

如线上问题必须优先处理，应先向用户说明当前功能状态和切换影响，得到确认后创建独立修复分支，并在进度文档中同时保留原功能和紧急修复的真实状态。

### 12.2 用户临时改变优先级

记录用户决定、原功能剩余事项和恢复入口，不丢弃已有工作，也不把暂停的功能错误标记为已收口。

### 12.3 无法完成

将状态更新为“阻塞”，记录已经尝试的方案、阻塞原因、所需条件和建议选择，并及时询问用户。
